# Operating Loop Architecture

Status: materialized bounded V1
Last updated: 2026-04-15

## Purpose

This document formalizes the current bounded V1 operating-loop shape of the proof.

The project is moving from a dashboard-centered proof toward a governed operational
decision system. The core loop is:

1. Demand creates service pressure.
2. Supply chain recommends and places replenishment orders.
3. Logistics recommends and executes inventory movements or sales fulfillment.
4. Receipts, transfers, and shipments change inventory state.
5. Inventory snapshots feed Gold outputs, the semantic model, Power BI, and the public site.

This is still a bounded public-safe proof. It is not an ERP, optimizer, writeback app,
warehouse-management system, or real-time operational control tower.

## Narrative Spine

Use this sequence across docs, dashboards, and interviews:

```text
Business problem
-> Operating loop
-> Bounded Fabric proof
-> Dashboard views
-> Public-safe release
```

The platform is important because it makes the loop governed and repeatable. The
platform is not the starting point of the story.

## MVP Scope

The first materialized implementation slice now exposes this causal path:

```text
supply-chain decision
-> purchase order line
-> supplier receipt
-> inventory snapshot update
-> Supply Chain Gold output
```

The same bounded pattern now also exposes first-pass tables for:

- inventory transfers
- sales fulfillment
- Sales Dashboard Gold outputs
- Inventory Decision Support Gold outputs
- a three-view semantic/report handoff for Power BI authoring

The remaining modeling gap is stricter inventory-ledger reconciliation. Current
snapshots are still generated by the representative-market engine, while the new event
ledger explains recommended and executed actions beside that snapshot state.

The remaining report gap is semantic-model table sync and Desktop/Service layout
authoring. The Lakehouse tables exist; the live report should not be described as
fully authored until the three-view contract has been implemented in Power BI.

## New Contract Families

### Master Data And Rule Tables

- `dim_supplier`: public-safe supplier entities.
- `rule_supplier_product_lead_time`: approved supplier, product, and receiving-location lead-time rules.
- `rule_location_transfer_lead_time`: approved origin and destination movement lead-time rules.
- `rule_location_service_lead_time`: approved service lead-time rules from a fulfillment location to an account or service region.

These tables explain what the system is allowed to plan. They are not execution facts.

### Recommendation Queues

- `fact_supply_chain_decision_queue_line`: replenishment recommendations.
- `fact_logistics_decision_queue_line`: movement and fulfillment recommendations.

Recommendation queues are advisory. A recommendation does not change inventory until it
is tied to an executed or planned event.

### Execution Facts

- `fact_purchase_order_line`: purchase-order lines created from approved supply-chain decisions.
- `fact_purchase_order_status_history`: status changes for purchase-order lines.
- `fact_inventory_movement_line`: inventory transfer shipments, in-transit movement, and arrivals.
- `fact_sales_fulfillment_line`: sales fulfillment events tied to demand lines.

Execution facts are the causal bridge between decisions and inventory state.

## Inventory State Rule

Future `fact_inventory_snapshot` rows should be explainable from prior state plus
executed events:

```text
ending_on_hand
= prior_on_hand
+ supplier receipts
+ transfer arrivals
- transfer shipments
- sales fulfillment shipments
```

Available inventory should remain separate from on-hand inventory whenever restricted,
reserved, or in-transit quantities are present.

In-transit inventory must not become available at the destination until its expected or
actual arrival date.

## Decision Status Rules

Use separate status concepts for recommendations and execution:

- recommendation status: `RECOMMENDED`, `APPROVED`, `REJECTED`, `DEFERRED`, `SUPERSEDED`
- purchase-order status: `PLANNED`, `ORDERED`, `PARTIALLY_RECEIVED`, `RECEIVED`, `CANCELLED`
- movement status: `PLANNED`, `SHIPPED`, `IN_TRANSIT`, `RECEIVED`, `CANCELLED`
- fulfillment status: `PLANNED`, `ALLOCATED`, `SHIPPED`, `DELIVERED`, `BACKORDERED`, `CANCELLED`

This separation prevents the model from pretending that every analytical
recommendation was executed.

## Public-Safe Region Policy

The proof should use public-safe service regions, not real coordinates or real customer
locations. Regions may be derived deterministically from safe account, service-network,
logistics-area, or site codes.

Do not publish real branch addresses, customer locations, warehouse coordinates, or
supplier identities.

## Validation Expectations

The operating loop is not credible unless validation proves:

- every recommendation resolves to approved public-safe dimensions
- executed events are tied to valid recommendations or documented generated rules
- lead-time dates are not earlier than their source dates
- purchase receipts do not exceed ordered quantity unless explicitly modeled
- movements conserve quantity across origin, transit, and destination
- fulfillment does not consume unavailable inventory without leaving backorder or open demand
- cost-effective V1 joins resolve without being described as finance-grade valuation
- snapshots can be reconciled from prior state plus executed events

## Explicit Deferrals

The following are not part of the first operating-loop implementation:

- real-time writeback
- Power Apps or custom transactional UI
- supplier optimization
- route optimization
- real geography
- anonymous public Power BI publishing
- enterprise-grade financial valuation
