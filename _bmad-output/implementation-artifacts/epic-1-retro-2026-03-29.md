# Epic 1 Retrospective: Publish a Safe Analytical MVP Slice

Date: 2026-03-29
Epic Status: done
Retrospective Status: done

## Epic Review

### Intended Outcome

Epic 1 was meant to produce one bounded, publication-safe analytical package that could be mirrored into the public site without leaking private structure, breaking contracts, or relying on ad hoc release behavior.

### What We Completed

- Story 1.1 established the governed repo, Astro baseline, and delivery boundaries.
- Story 1.2 published safe dimensions with deterministic abstraction rules.
- Story 1.3 added bounded facts and proxy metrics with public-safe nomenclature.
- Story 1.4 introduced a fail-closed sync from the approved package into the web mirror.
- Story 1.5 added blocking diagnostics for unsafe candidates and preserved approved baselines.
- Story 1.6 locked the publication manifest, sync contract, and verification baseline.

### What Went Well

- The epic stayed disciplined about boundaries. Public delivery, governed publication, and candidate validation remained clearly separated instead of drifting together.
- The team caught real governance issues during review rather than treating code review as a formality. The two strongest examples were the unrestricted sync boundary in Story 1.4 and the stale success-report path in Story 1.5.
- The package evolved from dimensions only to a believable analytical slice with facts, proxy metrics, candidate refresh behavior, and a public mirror without introducing runtime sprawl.
- Verification habits solidified early. By the end of the epic, package tests, validation, candidate refresh, web sync, and public-site build/check all had a stable documented path.

### What Was Harder Than Expected

- Naming and abstraction required more iteration than the first pass suggested. Several public field names and taxonomies were technically safe but still too close to the original business language.
- Governance features were easy to describe but required deeper hardening in practice. The most meaningful review findings were not syntax issues; they were operational boundary problems.
- The candidate lane created valuable safety, but it also introduced reporting responsibilities. It was not enough to fail safely; the system also had to leave honest evidence behind when a run failed.

### Key Discoveries

- Stable public identifiers matter more than simple deterministic ordering. The switch to stable hash-derived codes prevented renumbering drift across refreshes.
- A candidate lane is only trustworthy if it preserves the last-known-good state and also records blocked outcomes clearly.
- Public-safe storytelling needs its own layer of abstraction work. Technical safety alone is not the same thing as credible public framing.
- The public-site mirror boundary should be enforced by the sync command itself, not by operator discipline.

### Review Patterns

- The strongest review feedback focused on boundary enforcement and operational truthfulness rather than implementation syntax.
- The most useful corrections came from asking whether a command could be misused, whether a stale success signal could survive failure, and whether a public artifact revealed more business texture than intended.
- Fixing those issues improved both the code and the credibility of the portfolio story.

### Technical Debt and Open Risks

- The publication explorer notebook is useful but still rough around the edges and should become more self-maintaining over time.
- Trello mirroring is now helpful for visibility, but its attachment layer needs curated external-reader support rather than only metadata summaries.
- Epic 2 will now put more pressure on content clarity, route discipline, and public reading sequence than on data-pipeline mechanics.

## Next Epic Preparation

### Epic 2 Readiness

Epic 2 is ready to build on top of Epic 1. The approved package, candidate lane, publication mirror, and verification baseline now exist, so the site shell and route content can move faster without re-opening core publication mechanics.

### What Epic 2 Should Preserve

- Keep the shared public experience small and intentional.
- Do not blur the technical-method route into raw internal process dump territory.
- Keep freshness, release state, and publication-safe boundaries visible but calm.
- Avoid route and content expansion that makes the product feel like a generic portfolio catalog.

### Action Items

- Owner: Product direction
  Keep route responsibilities explicit so each Epic 2 page has one primary job in the reading sequence.

- Owner: Content and UX
  Translate governed data and technical proof into public language that feels confident, not evasive.

- Owner: Engineering
  Continue treating sync, validation, and release behavior as product features, not just internal scripts.

- Owner: Delivery discipline
  Keep code review focused on boundary drift, false trust signals, and misleading public language.

### Carry-Forward Agreements

- Public-safe nomenclature should favor abstraction that preserves behavior without hinting at the source business identity.
- Candidate outputs remain non-promoting by default.
- The public site should only consume approved mirrored artifacts.
- Each new public feature should stay inside the locked verification baseline unless there is an explicit reason to extend it.

## Closing Summary

Epic 1 delivered the governed spine of the project successfully. The most important result is not only that a safe package exists, but that the project now has believable rules for promotion, validation, evidence, and recovery. That gives Epic 2 a stable surface to build a trustworthy public experience on top of.
